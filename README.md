# Sakak Food Nutrition API

Implementation of assignment **2** using Python 3.12, FastAPI, PostgreSQL 16, SQLAlchemy 2, Alembic, and openpyxl. The existing `algorithm/algorithm.py` is unchanged.

The original `통합_식품영양성분DB_음식_20230715.xlsx` was not supplied in this workspace. The importer is tested with generated Excel workbooks; its mapping must still be verified against that exact source file before submission. No synthetic records are presented as the original dataset.

## Algorithm task (assignment 1)

The Look-and-Say sequence solution is in [`algorithm/algorithm.py`](algorithm/algorithm.py).

Run it from the repository root:

```sh
python3 algorithm/algorithm.py
```

Enter an integer `n` satisfying `3 < n < 100` when prompted. The script prints the nth sequence term and its two middle digits. For example, entering `5` prints `111221` and `result: 12`. This script uses only the Python standard library and runs independently of the API and database.

## Run with Docker

```sh
cp .env.example .env
```

## Import the original workbook

Place the supplied workbook in `data/`, retaining its filename:

```sh
docker compose exec api python -m nutrition.importer \
  /imports/통합_식품영양성분DB_음식_20230715.xlsx
```

The first worksheet and first row are used by default. Select a worksheet or a later header row when needed:

```sh
docker compose exec api python -m nutrition.importer \
  /imports/통합_식품영양성분DB_음식_20230715.xlsx \
  --sheet 'Sheet1' --header-row 1
```

A successful import prints `{"inserted": N, "skipped": M}`. Rerunning the same file inserts zero new records. `food_cd` is a database-enforced unique business key. `ON CONFLICT (food_cd) DO NOTHING` skips duplicates both within a file and across imports, including concurrent imports. Existing records, including API edits, are preserved; changes to existing foods must go through the API. A deleted record will be restored by reimporting its source row.

Rows are streamed with openpyxl's read-only mode and inserted in batches of 500. All batches belong to **one transaction**: an invalid row rolls back the entire import, and the error identifies the Excel row number. Unknown extra columns are ignored. All 16 mapped columns must be present; optional values within them may be empty. Missing or ambiguous mapped headers fail explicitly instead of silently losing nutrition data. Empty rows are ignored. No inferred values or unit conversions are applied.

After import, verify real data through the API (choose a food name present in the workbook):

```sh
curl --get http://localhost:8001/foods \
  --data-urlencode 'food_name=김치' --data 'page=1' --data 'page_size=5'
```

Check that `total` is positive, inspect the returned nutrients, and fetch a returned `id` through `/foods/{id}`. Import the same file again and confirm `inserted` is zero and the API total is unchanged. The automated import test performs this workflow with a generated workbook.

### Source mapping

Header whitespace is removed; `㎉` and `㎎` are normalized to `kcal` and `mg`. English API field names are also accepted as headers. The complete alias list is in `nutrition/importer.py`.

| Excel header (supported examples) | API field | Unit / type |
| --- | --- | --- |
| Generated by database, not Excel 번호 | `id` | integer |
| 식품코드 | `food_cd` | string, unique |
| 식품군 / 식품대분류 | `group_name` | string |
| 식품명 | `food_name` | string |
| 조사년도 / 조사연도 | `research_year` | integer, 1–9999 |
| 지역 / 제조사 | `maker_name` | string |
| 자료출처 | `ref_name` | string |
| 1회제공량 / 1회제공량(g) / 1회제공량(g/ml) | `serving_size` | numeric, source unit |
| 에너지(㎉) / 에너지(kcal) / 열량(kcal) | `calorie` | kcal |
| 탄수화물(g) | `carbohydrate` | g |
| 단백질(g) | `protein` | g |
| 지방(g) | `fat` | g |
| 총당류(g) / 당류(g) | `sugars` | g |
| 나트륨(㎎) / 나트륨(mg) | `sodium` | mg |
| 콜레스테롤(㎎) / 콜레스테롤(mg) | `cholesterol` | mg |
| 포화지방산(g) / 포화지방(g) | `saturated_fatty_acids` | g |
| 트랜스지방산(g) / 트랜스지방(g) | `trans_fat` | g |

Strings are trimmed. Empty cells and `-`, `--`, `N/A`, `NA`, `null`, `ND`, `N.D.`, `Tr`, `trace` (case-insensitive) become SQL NULL / JSON `null`, **not zero**. Trace and non-detect values are unknown quantities, so this API does not invent a measured value. A required food code/name cannot be missing. Nutrients and serving size must be finite and nonnegative; years must be integral. Thousands separators such as `1,234.5` are accepted. Invalid grouping, booleans, units embedded in numeric cells (`100g`), and inequality values (`<0.1`) are rejected for review. Food codes stored as Excel text preserve leading zeros; numeric Excel cells cannot recover already-lost leading zeros. Formula cells use cached values; use the source's value-only export if cached values are absent.

`serving_size` preserves the source's numeric quantity; nutrients are not rescaled to 100 g. The exact serving unit/basis must be confirmed in the source workbook. Floating-point values are appropriate for approximate nutritional measurements; this is not a medical calculation system.

## API contract

| Method | Endpoint | Result |
| --- | --- | --- |
| GET | `/foods` | Search/list, 200 |
| GET | `/foods/{id}` | One food, 200 or 404 |
| POST | `/foods` | Create, 201 + `Location` header |
| PATCH | `/foods/{id}` | Partial update, 200 or 404 |
| DELETE | `/foods/{id}` | Delete, 204 with empty body or 404 |

Both list items and detail responses include all 17 required fields. Requests reject unknown body fields and search parameters. Required fields for creation are `food_cd` (1–100 characters) and `food_name` (1–500 characters). Other fields default to `null`. Text fields have a 500-character limit. PATCH preserves omitted fields, allows clearing optional fields with `null`, rejects null required fields, and rejects an empty update. `food_cd` can be changed, subject to uniqueness.

### Search semantics

- `food_name` and `maker_name`: literal substring match, case-insensitive according to PostgreSQL's database collation. Korean matches directly; no fuzzy matching or internal whitespace normalization. `%` and `_` are escaped and treated literally.
- `food_code`: exact, case-sensitive match against response field `food_cd`.
- `research_year`: exact integer match.
- Leading/trailing whitespace is trimmed. Empty search strings are invalid.
- Provided conditions combine with AND; missing conditions impose no restriction.
- `page` starts at 1; default 1. `page_size` defaults to 20, maximum 100. Stable ordering is ascending `id`. Beyond the last page, `items` is empty.
- `total` is the count after filtering, before pagination. A repeatable-read transaction keeps count and items consistent within each PostgreSQL response. Separate requests may reflect intervening writes.

```sh
curl --get http://localhost:8001/foods \
  --data-urlencode 'food_name=김치' --data 'research_year=2023' \
  --data-urlencode 'maker_name=서울' --data 'page=1' --data 'page_size=20'

curl -i http://localhost:8001/foods \
  -H 'Content-Type: application/json' \
  -d '{"food_cd":"CUSTOM-001","food_name":"Example food","research_year":2023,"calorie":123.4,"protein":5}'

# Use the id returned by the previous request:
curl http://localhost:8001/foods/1
curl -X PATCH http://localhost:8001/foods/1 \
  -H 'Content-Type: application/json' -d '{"calorie":125,"ref_name":null}'
curl -i -X DELETE http://localhost:8001/foods/1
```

List shape:

```json
{"items": [], "total": 0, "page": 1, "page_size": 20}
```

### Errors and operations

| Status | Code | Example |
| --- | --- | --- |
| 404 | `not_found` | Missing detail, update, delete target or route |
| 409 | `conflict` | Duplicate food code on creation or update |
| 422 | `validation_error` | Invalid types, negative nutrients, unknown fields, invalid pagination, malformed JSON |
| 503 | `unavailable` | Health check cannot query database |
| 500 | `internal_error` | Unexpected server error; implementation details withheld |

```json
{"error":{"code":"not_found","message":"Food not found","details":null}}
```

Validation errors include `details` with a field location, message, and error type. Responses include a generated `X-Request-ID`. With `logging.json`, request logs include request ID, method, path, status and duration without logging request bodies or search parameters. `/health` queries the database. Docker checks it periodically.

## Local development and tests

Install [uv](https://docs.astral.sh/uv/) and use Python 3.12:

```sh
uv sync --frozen --python 3.12
# Start only the database for a locally running API:
docker compose up -d db
export DATABASE_URL='postgresql+psycopg://nutrition:nutrition@localhost:5433/nutrition'
uv run --frozen alembic upgrade head
uv run --frozen uvicorn nutrition.main:app --port 8001 --reload --log-config logging.json
```

`uv.lock` pins application and development dependencies. `.env` is read by Docker Compose; local commands use exported environment variables. Replace the URL if using a custom password or database port.

Quick tests use a temporary SQLite database per test:

```sh
uv run --frozen pytest -q
uv run --frozen ruff check nutrition tests migrations
uv run --frozen ruff format --check nutrition tests migrations
```

Run the same tests against PostgreSQL:

```sh
TEST_DATABASE_URL='postgresql+psycopg://nutrition:nutrition@localhost:5433/nutrition' \
  uv run --frozen pytest -q
```

Each PostgreSQL test creates a uniquely named schema and drops only that schema afterward. The test user needs schema-creation privileges and permission to install `pg_trgm` (or have it preinstalled in `public`). Do not use a production database for tests. Tests apply real Alembic migrations and verify upgrade/downgrade/re-upgrade. The GitHub Actions workflow runs PostgreSQL tests, lint, formatting, and a runtime image build.

For a fully containerized test run:

```sh
docker compose --profile test run --build --rm test
```

Tests cover combined filters, literal wildcard escaping, SQL injection strings, pagination, every CRUD operation, missing records, duplicate create/update, malformed inputs, nullable PATCH fields, request IDs, header mapping, missing data, numeric conversion, idempotency, preserving existing records, and rollback after an earlier batch has already been inserted.

## Design decisions and tradeoffs

- PostgreSQL provides transactions and unique constraints; the API relies on the database constraint for duplicate protection rather than a race-prone pre-check. SQLAlchemy binds values as parameters.
- Alembic owns schema creation. Deployments run migrations once before starting API replicas. `python -m nutrition.importer` also upgrades to the current migration before importing. No schema is automatically created by API workers.
- A B-tree unique index serves food-code lookup; `(research_year, id)` supports year filtering with ordered pagination. PostgreSQL `pg_trgm` GIN indexes on food/maker names support substring searches. Very short search terms can still require a scan. Migration credentials must be able to install this extension, or an administrator must preinstall it.
- Limit/offset pagination and exact counts are easy to evaluate for the assignment's dataset size. Large offsets and counts become expensive at much larger scale; a next step is cursor pagination plus optional counts.
- The importer uses O(batch size) Python row storage (plus workbook metadata), and PostgreSQL index lookups make duplicate handling efficient. One atomic import transaction favors consistent ingestion over incremental resumability; very large files could use a staging table and a separate validation/publish step.
- Imports deliberately avoid silently overwriting API changes. No authentication, rate limiting, caching, or distributed infrastructure is added to this assignment. Production work should add access control for mutations, operational limits, backups, and deployment-specific configuration.
- SQLite exists only as a quick test option; PostgreSQL is the deployment database and authoritative integration-test target.
